fish is a smart and user-friendly command line shell (like bash or zsh) with clever features that work out of the box, with nothing new to learn or configure.

fish-shell is approaching its 4.0 milestone, the first release since porting from C++ to Rust. Today we are announcing an open beta, inviting all users to try out the upcoming 4.0 release.

### **Try the fish-shell 4.0 beta at [fishshell.com](https://fishshell.com)**. View the [release notes here](https://fishshell.com/docs/current/relnotes.html).

If you are an existing fish user, or are curious to give it a try, this is a great opportunity to improve your command line experience while contributing to fish. Please report any issues you encounter by filing a [GitHub Issue](http://github.com/fish-shell/fish-shell/issues), or on our [Matrix channel](https://matrix.to/#/#fish-shell:matrix.org), which is also a great place to ask questions. Newbie questions welcome!

Even though most of the work for fish 4.0 went into the port, it has a few juicy features. We will be discussing those in a separate post, this post will discuss the mechanics of the port.

### By the numbers

The port was proposed in February 2023. January 2024 marked the elimination of C++ from the fish-shell codebase; this was then followed by a period of testing, fixes, and preparation for the release.

Prior to the port, fish-shell had over 49k lines of code in C++ source files, and nearly 8k lines in C++ header files. Today, fish has almost 72k lines of Rust.

A lot of that is down to how `rustfmt` formats code. It likes to split it across multiple lines. For instance, this C++:

```c++
return path_transform(parser, streams, argc, argv, wbasename);
```

turned into this rust:

```rust
path_transform(
    parser,
    streams,
    args,
    |s| wbasename(s).to_owned(),
    |opts| {
        opts.no_ext_valid = true;
    },
)
```

with the addition of one option.

The rest of the difference is down to Rust's explicit `use` constructs compared to C++'s umbrella headers, the need to re-implement `printf`, and some additional features added in the interim.

### Why port

fish-shell was originally written in C, in 2005. It was ported to C++ in 2011, for improved memory management, and C++ served fish-shell well for a decade.

But eventually, problems arose. Modern C++ is challenging to learn and makes it difficult to attract new developers. Over the 19 years of fish's existence, 193 people have touched the C++ or C code, but only 19 have at least 10 commits. For comparison, over 600 people have contributed to the .fish scripts shipped with the shell, with 50 having at least 10 commits.

We also try to make it as easy as possible to get the current fish version into people's hands, including on the long-term-support systems that are commonly used as servers. To that end we both build our own packages and try to make fish-shell easy to build. That limits us to C++11 even now, because upgrading the C++ compiler is a pain that every user on an LTS system would have to go through. C++ does not have an analogue to Rust's rustup. In addition, subjectively, the C++ releases after 11 don't offer too much.

fish-shell also has a long-term goal of enabling fully multithreaded execution of scripts (as an alternative to POSIX shell's subshells, as they are a very leaky abstraction), and prototypes of this in C++ proved unpromising. For example, it was too easy to accidentally share objects across threads, with only post-hoc tools like Thread Sanitizer to prevent it.

So we decided to port to a new language.

### How to port

A key requirement was that the port would be _incremental_: not a "big bang" rewrite, but instead one module or even function at a time, with a usable shell and all tests passing at each commit. This required strong language interoperability (i.e. an FFI), as both C++ and the target language would coexist for a period.

We maintained the existing style in the ported code. This resulted in code that was not exactly idiomatic, but was easier to compare and review.

For instance, early in the port we kept some places where we set errno to signal an error. This was a shortcut even in the C++ code, but we kept it at first and later replaced it with a proper error return. Or we changed for-loops to iterator chains once we were confident in the correctness of the ported code otherwise.

This is an ongoing effort. For instance we often use the libc crate directly where an abstraction would make the code nicer and quarantine some "unsafe" blocks.

Possibly the weirdest remnant of fish's earlier code is that we still use UTF-32 strings internally. This was a challenge and required some unusual string code. We hope this can be remedied in future.

### Why Rust

Rust was chosen because of a combination of an active and energetic community, the right architecture to support the port, and its concurrency guarantees.

Community is most important. Open-source projects live and die based on the community, on people volunteering their time. Rust has cultivated an active, enthusiastic community, with a systems programming bent. This community offers fish-shell a strong network of potential contributors. In a way, Rust being "cool" or at least interesting matters for an opensource project that wants to have people spend their free time on it.

Rust's underlying semantics are also similar to C++, which allowed for a straightforward, incremental port. In some ways fish's existing style also helped - we already used unique_ptr, and already did not use exceptions.

We used (forked) versions of [CXX](https://cxx.rs) and [autocxx](https://google.github.io/autocxx/) to allow C++ and Rust to interoperate. Had we chosen a language with (say) green threads or garbage collection, it would have complicated the FFI, and likely forced a redesign of fish's signal handling and async-signal-safe code.

But the killer feature of Rust, from fish-shell's perspective, is Send and Sync, statically enforcing rules around threading. "Fearless concurrency" is too strong - you can still blow your leg off with fork or signal handlers - but Send and Sync will be the key to unlocking fully multithreaded execution, with confidence in its correctness.

### The port

The port went more or less according to plan. Some new contributors pitched in, as we hoped - we would like to extend a special thank you to [Xiretza](https://github.com/Xiretza) and [henrikhorluck](https://github.com/henrikhorluck).

The easiest part to port were the builtins like `echo` or `math`. These basically operate like small self-contained programs with the usual argv and such, except they also have access to all of fish's innards (for instance `source` and `eval` need to be able to run code, while `set` needs to set variables). So the contributors could pick builtins and port them in parallel.

Other parts of fish, like the reader, proved too entangled to port separately, resulting in some large PRs.

Here is where our test suite paid off. We have a large base of integration tests that run fish scripts or exercise fish's interactivity, and we extended our unit tests quite a bit because rust makes it easy to do so.

But still, we introduced some bugs, discovered them and fixed them.

We ported some parts and ended up replacing them. For instance fish no longer links against (n)curses and instead uses the terminfo crate to read the terminfo database directly. This not only simplifies the code and the dependencies, but also allows us to fallback on "xterm-256color" definitions if the current terminal definition is unavailable.

The decision to keep the organization and style of the code paid off because it allowed us to easier compare the old and new code and notice parts that had been mistranslated or overlooked.

### Hurdles

Rust is powerful and widely appreciated, but we discovered areas of immaturity or missing features:

- Compile-time feature detection. For example, some systems may not have eventfd, which we use when available. The rust way to do this would be to litter the code with `#[cfg(any(bsd, target_os = "macos"))]`, enumerating the systems where it is, which fundamentally duplicates work already done by the libc crate.
  We wrote [our own crate](https://github.com/mqudsi/rsconf) to support configuration-time checks.

- Missing parts of libc. We expose libc macros like `_MNT_LOCAL` or `RLIMIT_SBSIZE` via a small C file, which (sadly) requires a C compiler.

- Universal macOS binaries, a surprise given Rust's reputation for cross-compilation. We implemented this manually with a shell script.

- Runtime format strings, which are needed for localization. We used gettext and (our own) printf instead of using `format!`.

- We [implemented printf](https://crates.io/crates/fish-printf), as the existing 'printf' crates in crates.io were not standards-conforming and/or required nightly Rust.
  This is needed because, as a shell, fish offers a `printf` builtin. So it is not just in our code, where most or all uses of printf could be replaced with another form of formatting, but directly exposed to scripts.

- In some places our direct reliance on the libc crate means that we are still more exposed to C weirdness than we would like to - for instance we have accidentally treated c_char as signed when it is unsigned on some platforms, and we still need to work around some platforms having `d_fileno` while others have `d_ino`

But the biggest surprise happened when we noticed that we would have to keep CMake for the time being. While fish itself can be built and run via cargo alone, we have over 1000 completion scripts, 229 functions and 131 man pages. Cargo is fine at handling the build, but won't handle these auxilliary files at all. We also build documentation via Sphinx and have a test suite that includes integration tests consisting of script files and interactive tests run with pexpect. We have a newfound respect for CMake, which has solved many of the problems we encountered, even as we transition off of it.

# Future direction

There are a lot of tasks related to the port that we would like to do or consider, as well as a lot of things that are enabled by having rust. Some that spring to mind:

- Replace our I-can't-believe-it's-not-yaml history format with a real format with a proper serializer
- Move off of UTF-32 strings
- Multi-threaded execution
- Move some of our libc use to a higher level crate like nix.
- Find a nicer translation system, given that gettext still has no support for extracting rust strings (and we have resorted to hacks)
- We have experimented with embedding the scripts inside of the fish binary, letting it install them. This allows fish to be installed via `cargo install`,
  and would make it possible to distribute single-file statically linked builds.
- Replace cmake, once we find a lighter alternative or cargo gains the necessary features.

# Conclusion

Overall, the 4.0 release consists of, at the time of writing, 471 closed issues and pull requests, 1128 files changed, 108539 inserted lines and 88794 deletions, excluding the translations.

It was a massive undertaking, and the Rust port was successful. Fish is the best it has ever been, and there is so much more on the horizon.

One thing that a lot of hay has been made about online is performance. During the port we explained that we did not know how it would shake out initially. The results now are promising: In our benchmark suite, most benchmarks are around ~10% faster. They use slightly more memory as a baseline, but some memory spikes have been removed. Overall, for a reasonably straighforward port that seems pretty good, and there are a lot of low-hanging fruit remaining.

Rust is NOT a feature of fish, but a foundation that enables new features, by making it easier for new contributors to join, and through Rust’s language capabilities.

If you are a fish user, Rust developer, or both, then this is a special time to get involved in fish. With the new Rust foundation, it’s easier than ever to contribute, and we are a laid-back, positive community. Contributions are welcome. Come join us!
